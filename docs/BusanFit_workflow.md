# BusanFit 일정 진단 워크플로우

## 1. 문서 목적

이 문서는 BusanFit의 핵심 기능인 **여행 일정 실행 가능성 진단 로직**의 기준을 정의한다.

BusanFit은 단순히 여행 일정을 생성하는 서비스가 아니라,
사용자가 만든 여행 일정이 실제로 실행 가능한지 판단하고
문제가 있다면 그 이유와 수정 방향을 제공하는 것을 목표로 한다.

---

## 2. 전체 진단 흐름

1. 여행 기본 정보 입력
2. 관광지 및 활동 선택
3. 관광지 상세 정보 조회
4. 관광지 기본 체류시간 계산
5. 활동별 추가 체류시간 계산
6. 날씨 및 혼잡도 보정
7. 관광지 간 이동시간 계산
8. 시간축 기반 일정 시뮬레이션
9. 관광지 운영시간 검증
10. 여행 종료시간 검증
11. 이동 동선 및 이동시간 비중 검증
12. 전체 진단 결과 생성
13. 관광지별 상세 진단 생성
14. 프론트에 진단 결과 반환

---

## 3. 사용자 입력

사용자는 다음 정보를 입력한다.

- 여행 날짜
- 여행 시작 시간
- 여행 종료 시간
- 출발 위치
- 방문할 관광지 목록
- 관광지 방문 순서
- 각 관광지에서 수행할 활동

출발 위치는 여행 일정 시뮬레이션의 시작점으로 사용한다.

예를 들어 사용자가 부산역에서 10:00에 출발하도록 설정했다면,
첫 관광지 도착시간은 10:00이 아니라
`부산역 → 첫 관광지 이동시간`을 더해서 계산한다.

예시:

```json
{
  "date": "2026-09-10",
  "startTime": "10:00",
  "endTime": "20:00",
  "startLocation": {
    "name": "부산역",
    "latitude": 35.1151,
    "longitude": 129.0414
  },
  "places": [
    {
      "placeId": 1,
      "activities": ["PHOTO", "WALK"]
    },
    {
      "placeId": 2,
      "activities": ["CAFE"]
    },
    {
      "placeId": 3,
      "activities": ["PHOTO", "SHOPPING"]
    }
  ]
}
```

## 4. 관광지 정보 조회

각 관광지에 대해 진단에 필요한 정보를 확보한다.

주요 정보:

- 관광지 이름
- 위도 / 경도
- 관광지 카테고리
- 운영시간
- 휴무일
- 기타 방문 제한 정보

관광지 정보 조회는 **공공데이터포털에서 발급받은 관광 관련 API**를 사용한다.

공공데이터포털 API 관리 페이지:

```text
https://www.data.go.kr/iim/api/selectAPIAcountView.do
```

한국관광공사 국문 관광정보 서비스 기본 엔드포인트:

```text
https://apis.data.go.kr/B551011/KorService2
```

개별 API 호출 시에는 위 기본 엔드포인트 뒤에
사용하려는 상세 오퍼레이션 경로를 붙여 요청한다.

예:

```text
https://apis.data.go.kr/B551011/KorService2/{operation}
```

진단 기능을 구현할 때 임의의 관광 데이터 API로 대체하지 않고,
프로젝트에서 발급받아 사용하기로 한 공공데이터포털 API를 우선 사용한다.

관광지 위치 정보는 이후 관광지 간 이동시간 계산에 사용한다.

### 4.1 API 인증키 관리 원칙

공공데이터포털 API의 인증키 또는 서비스키는
소스코드에 직접 하드코딩하지 않는다.

다음과 같은 방식으로 분리하여 관리한다.

```text
환경변수
또는
application.yml / application-local.yml 등의 설정 파일
```

예:

```yaml
external:
  public-data:
    service-key: ${PUBLIC_DATA_SERVICE_KEY}
```

운영 환경이나 Git 저장소에 실제 인증키가 노출되지 않도록 한다.

`.env`, 로컬 전용 설정 파일, IDE 환경변수 등을 사용할 경우
Git 추적 여부를 확인하고 실제 키가 커밋되지 않도록 관리한다.

## 5. 기본 체류시간 계산

관광지 카테고리에 따라 기본 체류시간을 설정한다.

초기 기준:

| 관광지 유형 | 기본 체류시간 |
|---|---:|
| 자연·야외 | 90분 |
| 문화·관광 | 60분 |
| 전시·실내 | 90분 |
| 쇼핑·시장 | 60분 |
| 레포츠·체험 | 120분 |

예:

```text
해운대해수욕장
카테고리: 자연·야외

기본 체류시간 = 90분
```

## 6. 활동별 추가 체류시간

사용자가 관광지에서 선택한 활동에 따라 체류시간을 추가한다.

현재 기준:

| 활동 | 추가시간 |
|---|---:|
| 카페 이용 | +40분 |
| 식사 | +60분 |
| 쇼핑 | +50분 |
| 사진 촬영 | +20분 |
| 산책 | +30분 |
| 관람·전시 | +60분 |
| 체험 프로그램 | +90분 |
| 전망·야경 감상 | +30분 |
| 휴식 | +20분 |
| 기타 활동 | +30분 |

예:

```text
해운대 기본 체류시간: 90분

사진 촬영: +20분
산책: +30분

총 체류시간: 140분
```

### 6.1 기타 활동 처리 원칙

`기타 활동`은 실제 일정에서 시간이 소요되는 활동으로 간주한다.

따라서 `0분`으로 처리하지 않고 기본값 `30분`을 적용한다.

```text
기본 체류시간 90분
+ 기타 활동 30분
= 총 체류시간 120분
```

현재 MVP에서는 모든 선택 활동 시간을 관광지 기본 체류시간에 단순 가산한다.

```text
최종 체류시간
=
관광지 기본 체류시간
+
선택한 활동 시간의 합
```

산책, 사진 촬영처럼 관광지 기본 체류시간 안에 일부 포함될 가능성이 있는 활동은
향후 실제 사용 결과를 바탕으로 중복 시간 보정 여부를 검토할 수 있다.

## 7. 날씨 및 혼잡도 처리

기상청 등의 API를 이용해
해당 날짜와 관광지 방문 예상 시간의 날씨를 확인한다.

BusanFit에서는 날씨를 이유로
관광지 체류시간이나 TMAP 이동시간에 임의의 보정시간을 직접 더하지 않는다.

즉, 다음과 같은 계산은 사용하지 않는다.

```text
TMAP 이동시간 30분
+ 비 보정 10분
= 40분
```

TMAP이 반환하는 예상 이동시간은
교통 및 경로 데이터를 기반으로 계산된 결과로 보고
BusanFit에서는 해당 값을 그대로 사용한다.

```text
이동시간
=
TMAP이 반환한 예상 이동시간
```

날씨 데이터는 주로 **활동 적합성 진단과 경고 메시지 생성**에 사용한다.

### 7.1 날씨에 따른 활동 경고

사용자가 선택한 활동 중
날씨의 영향을 많이 받는 활동이 있는 경우 경고를 생성한다.

대표적인 날씨 민감 활동:

- 사진 촬영
- 산책
- 전망·야경 감상

예:

```text
해운대 방문 예정 시간에 비가 예상됩니다.

선택한 활동 중
- 사진 촬영
- 산책

은 날씨의 영향을 받을 수 있습니다.
```

이 경우 활동시간은 그대로 유지한다.

```text
사진 촬영 +20분
산책 +30분
```

비가 온다는 이유만으로
해당 활동의 시간을 0분으로 만들거나 임의로 줄이지 않는다.

### 7.2 날씨 강도에 따른 진단

날씨의 강도에 따라 진단 수준을 다르게 적용할 수 있다.

예:

```text
약한 비
→ 활동시간 유지
→ 야외 활동 WARNING
```

```text
강한 비 또는 눈
→ 활동시간 유지
→ 강한 WARNING
```

```text
호우, 대설, 태풍 등
→ 야외 관광지 및 야외 활동에 대해
   WARNING 또는 IMPOSSIBLE 검토
```

핵심은 날씨가 체류시간을 자동으로 바꾸는 요소가 아니라,
**해당 활동과 일정이 실제로 적합한지 판단하는 요소**라는 점이다.

### 7.3 관광지 환경과 함께 판단

동일한 활동이라도
관광지가 실내인지 야외인지에 따라 날씨 영향이 다를 수 있다.

예:

```text
해운대 + 사진 촬영 + 비
→ 날씨 영향 큼
→ WARNING
```

```text
실내 전시관 + 사진 촬영 + 비
→ 날씨 영향 적음
→ 별도 경고 없음
```

따라서 향후에는 다음 요소를 함께 고려할 수 있다.

```text
관광지 환경
INDOOR / OUTDOOR

+

활동의 날씨 민감도

+

기상 상태
```

### 7.4 혼잡도 처리

혼잡도 데이터가 확보되는 경우
일정 위험도나 경고 메시지 생성에 사용할 수 있다.

다만 외부 경로 API가 이미 반영한 교통 영향을
BusanFit에서 임의의 시간 가산으로 다시 적용하지 않도록 한다.

혼잡도 기반 시간 보정이 필요한 경우에는
중복 보정 여부를 확인한 뒤 별도의 정책으로 정의한다.

## 8. 관광지 간 이동시간 계산

관광지 사이 이동시간은 TMAP 등의 경로 API를 사용해 계산한다.

입력 예:

```text
출발지: 해운대해수욕장
도착지: 광안리해수욕장
출발 예정 시간: 12:20
```

응답 예:

```text
예상 이동시간: 38분
```

BusanFit에서는 TMAP이 반환한 예상 이동시간을
일정 시뮬레이션에 그대로 사용한다.

```text
이동시간
=
TMAP 예상 이동시간
```

날씨 때문에 다음과 같이 별도의 시간을 추가하지 않는다.

```text
TMAP 예상 이동시간
+ 비 보정시간
```

이러한 별도 가산은 실제 교통 영향과 중복될 가능성이 있기 때문이다.

기상청 날씨 데이터는 이동시간 계산 자체가 아니라
야외 활동 경고 및 일정 위험도 판단에 사용한다.

이동시간은 일정 시뮬레이션에서 그대로 누적한다.

---

## 9. 시간 계산 원칙

### 9.1 분 단위 실제 시간 유지

BusanFit의 시간 계산에서는 임의의 시간 라운딩을 사용하지 않는다.

예:

```text
12:17 → 12:30
17:42 → 17:30
```

와 같은 정시 또는 30분 단위 반올림을 적용하지 않는다.

### 9.2 라운딩을 사용하지 않는 이유

라운딩을 적용하면 각 관광지를 지날 때마다 오차가 누적될 수 있다.

예:

```text
실제 해운대 종료: 12:17
이동시간: 38분
실제 광안리 도착: 12:55
```

이를 라운딩하면 실제 일정과 다른 도착시간이 생성될 수 있다.

관광지가 여러 개일 경우 작은 오차가 누적되어
마지막 관광지에서는 큰 시간 차이가 발생할 수 있다.

또한 운영 종료시간과 가까운 일정에서는
라운딩 때문에 방문 가능 여부 자체가 잘못 판단될 수 있다.

따라서 모든 진단 계산은 **분 단위 실제 시간**을 유지한다.

## 10. 시간축 기반 일정 시뮬레이션

진단 엔진은 여행 시작시간부터
각 관광지를 순서대로 방문한다고 가정하여 시간을 누적한다.

기본 흐름:

```text
현재 시간
↓
관광지 도착
↓
체류시간 추가
↓
관광지 출발
↓
이동시간 추가
↓
다음 관광지 도착
↓
반복
```

예:

```text
여행 시작
부산역 10:00 출발

↓ 부산역 → 해운대 이동 50분

해운대 도착
10:50

↓ 해운대 체류 137분

해운대 출발
13:07

↓ 해운대 → 광안리 이동 20분

광안리 도착
13:27

↓ 광안리 체류 103분

광안리 출발
15:10

↓ 광안리 → 감천문화마을 이동 47분

감천문화마을 도착
15:57
```

첫 관광지의 도착시간도 반드시 출발 위치에서의 이동시간을 포함해 계산한다.

```text
첫 관광지 도착시간
=
여행 시작시간
+
출발 위치 → 첫 관광지 이동시간
```

이후 관광지는 다음과 같이 계산한다.

```text
관광지 출발시간
=
관광지 도착시간
+
관광지 체류시간

다음 관광지 도착시간
=
현재 관광지 출발시간
+
현재 관광지 → 다음 관광지 이동시간
```

## 11. 일정 시뮬레이션 기본 알고리즘

개념적인 형태는 다음과 같다.

```java
LocalDateTime currentTime = tripStartTime;

// 출발 위치에서 첫 관광지까지 이동
Place firstPlace = places.get(0);

long firstTravelMinutes =
        getTravelMinutes(
                startLocation,
                firstPlace,
                currentTime
        );

currentTime =
        currentTime.plusMinutes(firstTravelMinutes);

for (int i = 0; i < places.size(); i++) {

    Place place = places.get(i);

    LocalDateTime arrivalTime = currentTime;

    long stayMinutes =
            baseStayMinutes
            + activityMinutes;

    LocalDateTime departureTime =
            arrivalTime.plusMinutes(stayMinutes);

    validateOpeningHours(
            place,
            arrivalTime,
            departureTime
    );

    if (i < places.size() - 1) {

        Place nextPlace = places.get(i + 1);

        long travelMinutes =
                getTravelMinutes(
                        place,
                        nextPlace,
                        departureTime
                );

        currentTime =
                departureTime.plusMinutes(travelMinutes);

    } else {
        currentTime = departureTime;
    }
}
```

## 12. 운영시간 검증

계산된 관광지 도착시간과 출발시간을
해당 관광지 운영시간과 비교한다.

예:

```text
감천문화마을 운영시간
09:00 ~ 18:00

예상 도착시간
18:30
```

이 경우 해당 관광지는 정상적으로 방문할 수 없는 것으로 판단한다.

진단 결과에는 단순히 실패 여부만 반환하는 것이 아니라
구체적인 이유를 함께 제공한다.

예:

```text
감천문화마을 예상 도착 시간이 18:30이지만
운영 종료 시간이 18:00입니다.
```

---

## 13. 여행 종료시간 검증

모든 관광지 방문이 끝난 예상 종료시간과
사용자가 설정한 여행 종료시간을 비교한다.

예:

```text
사용자 설정 종료시간: 20:00
예상 일정 종료시간: 21:30
```

결과:

```text
예상 종료시간이 설정한 종료시간보다
1시간 30분 초과합니다.
```

이 경우 전체 일정은 실행이 어렵다고 판단할 수 있다.

---

## 14. 이동시간 및 동선 검증

BusanFit은 단순히 시간 안에 일정이 들어오는지만 확인하지 않는다.

다음 정보도 계산한다.

- 전체 여행시간
- 전체 관광지 체류시간
- 전체 이동시간
- 전체 시간 중 이동시간이 차지하는 비율

예:

```text
총 여행시간: 10시간
총 관광시간: 5시간
총 이동시간: 4시간
기타: 1시간
```

이동시간의 비율이 지나치게 높은 경우
일정은 실행 가능하더라도 비효율적인 일정으로 판단할 수 있다.

예:

```text
전체 일정의 약 40%가 이동시간입니다.
관광지 방문 순서를 조정하는 것을 권장합니다.
```

## 15. 전체 진단 상태

최종 결과는 다음과 같은 상태로 구분할 수 있다.

### AVAILABLE

일정 실행에 큰 문제가 없는 상태.

예:

- 운영시간 문제 없음
- 여행 종료시간 초과 없음
- 이동시간 과다 문제 없음

### WARNING

일정 실행은 가능하지만 조정이 권장되는 상태.

예:

- 이동시간 비중이 높음
- 악천후 예상
- 관광지 간 거리가 큼
- 일정 여유시간이 매우 적음

### IMPOSSIBLE

현재 일정으로 정상적인 실행이 어려운 상태.

예:

- 관광지 운영시간 초과
- 여행 종료시간 초과
- 휴무일 방문
- 필수 방문 조건 충족 불가

## 16. 관광지별 상세 진단

각 관광지에 대해 다음 정보를 생성한다.

- 관광지 이름
- 예상 도착시간
- 예상 출발시간
- 예상 체류시간
- 이전 관광지에서의 이동시간
- 방문 가능 여부
- 문제 발생 시 진단 이유

예:

```text
해운대해수욕장

도착: 10:00
출발: 12:17
체류시간: 137분
상태: AVAILABLE
```

예:

```text
감천문화마을

도착: 18:30
운영 종료: 18:00

상태: IMPOSSIBLE

이유:
예상 도착시간이 관광지 운영 종료시간보다 늦습니다.
```

## 18. 프론트 표시

프론트에서는 진단 결과를 사용자가 이해하기 쉬운 형태로 보여준다.

예:

```text
일정 조정 필요

10:00 해운대 도착
12:17 해운대 출발

12:55 광안리 도착
14:38 광안리 출발

18:30 감천문화마을 도착

문제
감천문화마을 운영 종료시간은 18:00입니다.

추천
감천문화마을 방문 순서를 앞쪽으로 변경하세요.
```

진단 결과 화면에서는 지도 보기 기능을 제공할 수 있으며,
지도 화면에서는 사용자가 선택한 관광지의 실제 이동 동선을 표시한다.

## 19. 프론트 상태 관리와 데이터 저장 원칙

BusanFit에서는 Zustand, TanStack Query, Spring Boot, MySQL의 역할을 명확히 분리한다.

### 19.1 Zustand 역할

Zustand는 사용자가 현재 만들고 있는 여행 일정의 **클라이언트 상태**를 관리한다.

예:

- 여행 날짜
- 여행 시작 시간
- 여행 종료 시간
- 출발 위치
- 선택한 관광지
- 관광지 방문 순서
- 각 관광지에서 선택한 활동

예시:

```ts
{
  date: '2026-09-10',
  startTime: '10:00',
  endTime: '20:00',
  startLocation: {
    name: '부산역',
    latitude: 35.1151,
    longitude: 129.0414
  },
  places: [...]
}
```

Zustand에 저장되는 값은 사용자가 현재 화면 흐름에서 작성 중인 일정 상태이며,
DB에 영구 저장되는 데이터와는 구분한다.

### 19.2 TanStack Query 역할

TanStack Query는 프론트에서 백엔드 API 요청과 응답 상태를 관리한다.

주요 역할:

- 진단 API 호출
- 로딩 상태 관리
- 에러 상태 관리
- 응답 데이터 캐싱
- 필요 시 재조회

예:

```ts
useMutation({
  mutationFn: diagnoseTrip
})
```

진단 API 응답 예:

```ts
{
  status: 'WARNING',
  expectedEndTime: '18:42',
  stops: [...]
}
```

TanStack Query의 캐시는 MySQL 같은 영구 저장소가 아니다.

따라서 TanStack Query에 데이터가 존재한다고 해서
해당 데이터가 서버 DB에 저장된 것은 아니다.

### 19.3 Spring Boot 역할

Spring Boot 백엔드는 실제 일정 진단 로직을 수행한다.

기본 흐름:

```text
프론트 진단 요청
↓
Spring Boot
↓
TourAPI 조회
TMAP 조회
기상청 조회
↓
일정 시간축 시뮬레이션
↓
운영시간 / 종료시간 / 날씨 위험도 검증
↓
최종 진단 결과 생성
↓
프론트 반환
```

외부 API 호출 결과는 진단 계산에 사용하고,
필요하지 않은 원본 응답 전체를 MySQL에 저장하지 않는다.

### 19.4 외부 API 응답 저장 원칙

다음과 같은 외부 API 결과는 기본적으로 DB에 직접 저장하지 않는다.

- TMAP 예상 이동시간
- 기상청 날씨 정보
- TourAPI에서 조회한 실시간 또는 변경 가능 정보
- 기타 진단 시점에 조회한 외부 API 응답 원본

이유:

- 시간이 지나면 값이 오래될 수 있다.
- 교통상황과 날씨는 계속 변한다.
- 운영시간 등 외부 정보도 변경될 수 있다.
- 진단 시점의 최신 데이터를 사용하는 것이 더 중요하다.

따라서 기본 원칙은 다음과 같다.

```text
사용자 진단 요청
↓
외부 API 조회
↓
메모리에서 진단 계산
↓
진단 결과 생성
↓
프론트 반환
```

### 19.5 MySQL에 저장할 데이터

MySQL에는 사용자가 실제로 저장하기로 한 일정이나
서비스에서 영구 보관할 필요가 있는 결과만 저장한다.

예:

- 사용자 ID
- 여행 날짜
- 여행 시작 시간
- 여행 종료 시간
- 출발 위치
- 관광지 목록
- 관광지 방문 순서
- 선택 활동
- 진단 당시 계산된 도착시간
- 진단 당시 계산된 출발시간
- 전체 진단 상태
- 진단 이유 및 경고 메시지

즉, 외부 API 원본 응답을 그대로 저장하는 것이 아니라
**사용자 일정과 최종 진단 결과**를 저장한다.

### 19.6 전체 역할 정리

```text
Zustand
→ 사용자가 현재 작성 중인 일정 상태

TanStack Query
→ 백엔드 API 요청 / 응답 / 캐시 / 로딩 / 에러 관리

Spring Boot
→ 외부 API 호출 + 일정 진단 로직 실행

MySQL
→ 사용자가 저장한 일정과 진단 결과 영구 저장
```

### 19.7 전체 데이터 흐름

```text
사용자 입력
↓
Zustand
↓
진단 버튼 클릭
↓
TanStack Query
↓
Spring Boot 진단 API 호출
↓
TourAPI / TMAP / 기상청 조회
↓
일정 진단 엔진 실행
↓
진단 결과 반환
↓
TanStack Query 캐시에 보관
↓
결과 화면 표시

사용자가 "일정 저장" 선택
↓
저장 API 호출
↓
MySQL에 일정 및 진단 결과 저장
```

## 20. 핵심 설계 원칙

BusanFit 일정 진단 기능은 다음 원칙을 따른다.

1. 시간을 임의로 반올림하지 않는다.
2. 모든 시간 계산은 분 단위 실제 값을 유지한다.
3. 사용자가 설정한 출발 위치와 출발 시간을 일정 시뮬레이션의 시작점으로 사용한다.
4. 첫 관광지 도착시간에도 출발 위치에서 첫 관광지까지의 이동시간을 반드시 반영한다.
5. 관광지 방문 순서를 기준으로 시간을 순차 누적한다.
6. 관광지 정보는 공공데이터포털 한국관광공사 국문 관광정보 서비스(`https://apis.data.go.kr/B551011/KorService2`)를 기준으로 조회한다.
7. 공공데이터포털 API 인증키는 소스코드에 하드코딩하지 않고 환경변수 또는 설정 파일을 통해 주입한다.
8. TMAP 등 외부 경로 API가 반환한 예상 이동시간을 실제 일정 계산에 그대로 반영한다.
9. 날씨 때문에 이동시간에 임의의 보정시간을 추가하지 않는다.
10. 날씨는 체류시간을 자동으로 줄이거나 늘리는 요소가 아니라 활동 적합성과 일정 위험도를 판단하는 요소로 사용한다.
11. 관광지 운영시간을 예상 도착시간과 비교한다.
12. 사용자가 지정한 여행 종료시간을 반드시 검증한다.
13. 외부 API 원본 응답은 기본적으로 MySQL에 저장하지 않는다.
14. 외부 API 데이터는 진단 시점의 계산에 사용하고, 필요한 최종 진단 결과만 저장한다.
15. Zustand는 현재 작성 중인 일정 상태를 관리하고, TanStack Query는 API 요청과 응답 캐시를 관리한다.
16. 단순 성공/실패가 아니라 실패 이유를 함께 반환한다.
17. 전체 일정과 개별 관광지의 진단 결과를 모두 제공한다.
18. 가능 여부뿐 아니라 이동시간 과다, 날씨 등 주의 요소도 진단한다.
19. 외부 API 호출 자체보다 여러 데이터를 결합하여 일정 실행 가능성을 판단하는 로직을 핵심 기능으로 본다.

## 21. 핵심 기능 정의

BusanFit의 일정 진단 기능은 다음과 같이 정의한다.

> 사용자의 여행 일정을 시간축으로 시뮬레이션하고,
> 관광지 운영시간, 예상 체류시간, 관광지 간 이동시간,
> 날씨 및 혼잡도 등의 위험 요소를 종합하여
> 해당 일정의 실제 실행 가능 여부를 판단하고
> 문제점과 수정 방향을 제공하는 기능.
