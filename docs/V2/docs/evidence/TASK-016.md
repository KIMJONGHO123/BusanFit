# TASK-016 계획 — 관광지 데이터 연결·보완정보 저장 및 조회

상태: **출처별 수동 적재 구현 및 실제 MySQL 저장 완료 — TourAPI 353건·부산명소정보 213건. 구현 리뷰 CHANGES_REQUIRED의 P2 수정·재검증 완료. 개발자 최종 확인 및 커밋·푸시 승인**.
작성일: 2026-11-03.
개발자는 앞서 제안한 TASK-016 방향을 수용하고, 우선 이 파일에 데이터 연결 계획만 작성하도록 지시했다. 이후 작업은 TASK-016에서 발견되는 사항을 보고 정하며, 별도 Task 문서를 미리 만들지 않는다.

## 1. Task ID

`TASK-016`

## 2. Goal

TourAPI와 부산명소정보의 장소 연결·보완 저장·조회 계획을 유지하면서, 후속 지시에 따라 실제 출처별 데이터를 확보해 DB에 저장한다.
기존 `tourapi-{contentid}`를 유지하며, 장소 연결 성공과 개별 정보의 확인 성공을 구분한다. 현재 실행 범위는 6.11절의 수동 수집·저장이며 전체 장소 연결·검색 통합 구현 완료를 의미하지 않는다.

### 이 계획이 다루는 구현 범위

- 부산 관광지에 한해 TourAPI `contentid`와 부산명소정보 `UC_SEQ`를 연결한다.
- 확실한 대상은 자동 연결하고, 나머지 후보는 개발자가 확인한다.
- TourAPI의 빈 정보를 부산명소정보로 보완한다.
- 저장된 연결을 이용해 기존 검색 결과와 장소 조회에 보완정보를 결합한다.
- 보완정보를 웹에 노출할 때 항목별 실제 출처를 표시하도록 기존 출처 문구를 최소 수정한다. 레이아웃·사용 흐름 개편과 구분한다.
- 초기 적재와 검토 결과 반영은 명시적으로 실행하는 방식으로 설계한다. 요청 때마다 전체 데이터를 수집하거나 장소를 다시 비교하지 않는다.

### 제외 범위

## 6. Codex A 주요 판단

### 6.1. 기존 구조 확인

- 현재 `/api/places/search`는 `PlaceController`에서 `TourApiClient`를 직접 호출한다.
- 현재 `PlaceSearchResult`에는 장소 ID·이름·주소·분류·좌표·이미지·기존 체류시간 필드가 있다. 보완정보와 출처를 모두 표현하는 상세 조회 계약은 별도 설계가 필요하다.
- 진단의 `TourismPort.findPlace`는 현재 `TourApiTourismAdapter`를 통해 장소 이름·좌표·지역을 조회한다. 운영정보를 저장했다고 기존 운영시간 미지원 상태를 해제하지 않는다.
- 향후 검색·조회 응용 서비스에서 저장된 보완정보를 결합하고, 외부 DTO와 JPA 모델을 Diagnosis Domain으로 직접 전달하지 않는다.
- 최초 저장 구조 재확인: 저장 관련 의존성은 Spring Data JPA·MySQL이며 기존 테스트는 H2를 사용했다. 당시 코드의 JPA Entity/Repository는 사용자 영역에 있었고 장소 저장 및 Flyway/Liquibase 구성은 없었다. 이후 실제 DB 확인과 별도 적재 구현 결과는 6.11절에 기록한다.
- 현재 웹 상세는 검색 결과 객체를 표시한다. 별도 장소 상세 API와 출처별 보완 응답 계약은 아직 없다. 검색은 실시간 TourAPI, 진단의 장소 확인도 TourAPI 호출이며, DB에서 두 출처를 읽는 구조가 이미 구현되었다고 설명하지 않는다.

### 6.2. 자동 연결 기준

다음 조건을 모두 만족할 때만 자동 연결한다.

| 항목 | 기준 |
|---|---|
| 지역 | 양쪽 모두 부산으로 확인되어야 한다. 이름에 부산이 포함된다는 이유로 지역을 추정하지 않는다. |
| 이름 | 공백·단순 구두점 정리 후 일치해야 한다. 본점·분관·입구·전망대 등 식별 의미를 가진 단어는 보존한다. |
| 주소 | 동일 체계의 도로명·건물번호 또는 지번이 일치해야 한다. 도로명과 지번 간 대응을 확인하지 못하면 일치로 추정하지 않는다. |
| 좌표 | 유효한 위경도 간 지표면 거리가 100m 이하여야 한다. |
| 유일성 | 양쪽 출처의 수집 완료된 부산 관광지 연결 대상 전체를 기준으로 서로 유일한 적격 연결 대상이어야 하며, 기존 유효 연결과 충돌하지 않아야 한다. 개별 페이지나 일부 표본만으로 확정하지 않는다. |
| 시설 범위 | 관광지 전체와 내부 시설, 입구 등 서로 다른 대상을 합치지 않는다. 동일 범위를 확인할 수 없으면 검토 대상으로 남긴다. |

- 이름 정규화가 괄호 안 시설명 등 의미 있는 내용을 제거하지 않도록 한다. 구체적인 정규화 목록과 경계 사례는 구현 시 테스트로 고정한다.
- 주소·좌표 누락, 이름 차이, 복수 후보, 다른 시설 범위 또는 100m 초과는 자동 연결하지 않는다.
- 100m는 초기 자동 연결 상한이다. 넓은 관광지의 좌표 차이는 개발자가 별도로 확인할 수 있다. 실제 표본에서 기준 변경이 필요하면 근거를 보고하고 개발자 결정 후 변경한다.
- 후보 탐색과 자동 연결을 구분한다. 후보 검색의 거리·유사도만으로 연결을 승인하지 않으며, 실제 데이터 표본을 확인한 뒤 후보 검색 방식의 세부값을 정한다.
- 초기에는 양쪽 ID 간 일대일 연결을 원칙으로 한다. 다대일·일대다 사례가 나오면 별도 판단 대상으로 보고한다.
- 양쪽 대상 전체의 페이지 수집과 누락·중복 검사를 마친 뒤 유일성을 평가한다. 일부 페이지의 수집·파싱 실패 또는 누락·중복으로 전체 수집 완료를 확인하지 못하면 해당 수집 실행의 자동 연결을 보류한다. 수집된 일부 페이지만으로 연결하지 않으며, 뒤 페이지에서 발견한 경쟁 후보도 전체 후보 집합에 포함한다.

### 6.3. 개발자 검토와 연결 상태

- 검토 파일에는 양쪽 ID·이름·주소·좌표·거리, 자동 연결하지 않은 사유와 기존 연결 유무를 포함한다.
- 초기에는 별도 관리자 UI 없이 파일로 후보를 내보내고 개발자가 승인·거절한 결과를 검증 후 반영하는 방식을 사용한다.
- 검토 결과 반영 시 대상 ID·입력 데이터 버전·기존 연결을 다시 확인한다. 오래된 검토 결과로 바뀐 장소를 연결하거나 기존 연결을 덮어쓰지 않는다.
- 연결 상태는 미연결·검토 대기·연결됨·거절·재검토 필요를 구분한다. 명칭과 실제 저장 형식은 구현 시 확정한다.
- 자동/수동 연결 구분, 판단 근거, 기준 버전, 확인 시각과 검토 주체를 기록한다.
- 거절한 후보는 이름·주소·좌표 등 연결 근거가 그대로라면 반복 제안하지 않는다. 근거가 바뀌면 이전 판단을 보존하고 재검토 대상으로 분리한다.
- 연결 근거의 의미 있는 변경을 발견하면 임의로 새 장소에 재연결하지 않는다. 해당 연결의 부산 보완정보 사용을 중지하고 개발자에게 재확인을 요청한다. 변경 감지의 세부 기준은 구현 전 표본으로 구체화한다.
- 연결이 없거나 검토 중이어도 기존 TourAPI 검색·일정 구성을 사용할 수 있다. 부산 보완정보 미확인을 장소 부재로 처리하지 않는다.

### 6.4. 정보 보완과 충돌

| 상태 | 조회·저장 원칙 |
|---|---|
| TourAPI에 유효한 값이 있음 | 기본 표시값으로 유지한다. |
| TourAPI 값이 비고 부산 값이 있음 | 확인된 연결에 한해 부산 값으로 보완하고 출처를 표시한다. |
| 양쪽 값이 같거나 의미가 같음을 확인함 | 출처별 값을 보존하고 일치 근거를 남긴다. |
| 서로 다른 의미이거나 동일 의미 여부가 불명확함 | 양쪽 값과 차이·확인 상태를 보존한다. 임의로 진단 근거를 확정하지 않는다. |
| 양쪽 모두 값이 없음 | 미확인으로 유지한다. |

- 수집 대상은 운영일·휴무일·운영시간·요금·설명·연락처·홈페이지·교통정보·편의시설·이미지 등 서비스에 필요한 정보다. 제공되지 않는 항목은 추정 생성하지 않는다.
- null·빈 문자열·공백은 값 없음으로 정리한다. `무료`, `휴무 없음`, `상시 개방`처럼 의미가 있는 값을 빈 값으로 제거하지 않는다. 표현을 해석할 수 있다는 것과 진단에 적용할 수 있다는 것은 구분한다.
- 문구를 억지로 요약하거나 합쳐 새로운 운영시간을 만들지 않는다. 예를 들어 TourAPI `09:00~18:00`와 부산 `10:00~17:00`를 `09:00~17:00`로 합치지 않는다.
- 운영정보의 차이가 해결되지 않으면 영향을 받는 조건은 검증 불가로 유지한다. 충돌의 상세 해소와 운영시간 평가 구현은 이번 범위 밖이다.
- 장소 연결 성공만으로 모든 항목을 확인됨으로 표시하지 않는다. 부산에서만 보완된 이미지 등을 TourAPI 출처로 표시하지 않는다.
- 현재 웹 상세의 `PlaceSearchPage.tsx`는 출처를 `장소 정보 · 한국관광공사`로 고정 표시한다. 보완정보 노출 구현 시 표시한 항목·이미지의 실제 출처에 맞게 문구를 수정한다. 검색 목록의 `한국관광공사 제공`도 목록 데이터의 출처와 보완 항목의 출처가 혼동되지 않게 구분한다. 필요한 응답 출처 필드와 표시만 최소 수정하며 웹 화면 개편으로 범위를 넓히지 않는다.

### 6.5. 저장 개념과 실패 처리

구체적인 테이블명·컬럼·인덱스·마이그레이션은 구현 시작 시 기존 저장 구조와 실제 응답 표본을 확인한 뒤 설계한다. 필요한 저장 개념은 다음과 같다.

| 개념 | 저장할 내용 |
|---|---|
| 출처별 장소 정보 | 제공기관·외부 ID·이름·주소·좌표·확인된 지역 및 서비스용 정보 |
| 장소 연결 | 공통 장소 ID·부산 콘텐츠 ID·연결 상태·방식·근거·기준 버전 |
| 항목별 보완정보 | 출처별 값·선택한 표시값과 출처·누락 및 충돌 상태 |
| 확인 시각 | 마지막 정상 수집 확인 시각, 제공기관 수정 시각이 있으면 별도 보관 |
| 검토 이력 | 승인·거절·재검토의 근거·주체·시각·판단 대상 버전 |
| 적재 결과 | 실행 식별자·성공/실패·처리 건수와 마스킹한 실패 사유 |

- 외부 API 응답 전체를 무분별하게 저장하지 않는다. 선택한 항목의 출처별 원문 값과 판단 근거를 필요한 범위에서 보존한다.
- 동일 데이터를 다시 반영해도 연결·보완정보가 중복 생성되지 않게 한다. 잘못된 중복 연결은 저장 제약과 응용 계층 양쪽에서 막는다.
- 최초 적재는 수동 실행을 전제로 한다. 전체 수집이 필요한 작업에서는 페이지 누락·중복·실패 여부를 확인한 뒤 정상 수집 단위를 반영한다. 중간 실패를 완전한 빈 결과로 간주하지 않는다.
- 정상 수집 단위의 저장과 자동 연결 확정은 구분한다. 일부 데이터를 저장했더라도 6.2절의 전체 수집 완료 조건을 확인하기 전에는 해당 실행의 자동 연결을 반영하지 않는다. 실패 실행으로 기존 유효 연결과 보완정보를 덮어쓰지 않는다.
- 조회·수집 실패 시 기존 데이터와 마지막 정상 확인 시각을 보존하고 실패 사실을 구분한다. 성공하지 않은 요청으로 확인 시각을 갱신하지 않는다.
- 정상 응답에서 특정 값의 부재가 확인된 경우와 통신·파싱 실패로 값을 모르는 경우를 구분한다. 이전 값만으로 현재 항목을 확인됨으로 표시하지 않는다.
- 목록에서 한 번 보이지 않았다는 이유로 장소를 삭제하거나 폐업으로 판단하지 않는다. 삭제·ID 변경의 상세 운영 정책은 발견 사례를 보고 별도로 정한다.
- 수집 확인 시각은 현장 정보의 정확성이나 방문일 적용 가능성을 보장하지 않는다. 이번 계획에서는 정보 사용 기한을 새로 확정하지 않는다.

### 6.6. 조회 흐름과 경계

1. 기존 TourAPI 검색으로 장소 목록과 공통 장소 ID를 얻는다.
2. 결과의 ID 목록으로 저장된 유효 연결·보완정보를 일괄 조회한다. 장소마다 DB 조회를 반복하는 구조를 피한다.
3. 항목별 보완 기준에 따라 응답을 구성하고 출처·미확인·충돌 상태를 표현한다.
4. 상세 용도의 정보는 별도 조회 모델로 제공할 수 있게 설계한다. 기존 검색의 ID·순서·페이지 동작을 임의로 바꾸지 않는다.
5. 진단 연결에 필요한 정보는 Port 뒤에서 내부 모델로 변환한다. 저장된 운영정보가 생겼다는 이유로 미구현 Rule을 PASS로 바꾸지 않는다.

- 부산 데이터 변환은 부산 Adapter에, 저장 접근은 Repository 경계에 둔다. 장소 연결·보완 조회는 장소 관리 책임으로 구성한다.
- 방문 가능 여부와 Rule 선택 책임은 기존 Diagnosis Domain·Rule Registry에 유지한다. 부산 데이터를 사용했다는 이유로 전국 공통 운영시간 Rule 자체를 부산 전용으로 바꾸지 않는다.
- 타 지역·지역 미확인 장소에 부산 보완정보를 적용하지 않는다. 기존 지역 미확인 결과를 부산 데이터로 임의 해소하지 않는다.
- 부산 API 장애·미연결로 TourAPI의 정상 검색을 빈 목록이나 mock으로 대체하지 않는다. 보완 저장소 장애도 실제 실패로 구분하며 정상 보완 완료로 표시하지 않는다.
- 보완 필드의 응답 형식은 구현 시 기존 웹 계약을 확인해 호환되게 정한다. 이 계획에서 새 API 응답 계약을 확정한 것으로 취급하지 않는다.
- 사용자 활동·최종 `plannedStaySeconds`·기존 시간 계산과 판정 집계는 변경하지 않는다. 장소 정보로 근거 없는 권장 체류시간을 생성하지 않는다.

### 6.7. 향후 구현 순서

1. 6.8~6.10절의 저장·조회 설계안을 먼저 검토한다. 검색 기준, 테이블·PK/FK·제약·저장 필드·이력·실패 처리 및 응답 계약을 구현 전에 구체화하고 개발자 판단이 필요한 선택을 확정한다.
2. 실제 응답 표본에서 이름·주소·좌표·시설 범위와 필요한 보완 필드를 확인한다. 출처별 API/항목과 저장 컬럼 대응표를 완성하고, 연결 가능·애매함·불일치 사례를 정리한다. 설계와 맞지 않으면 설계안을 먼저 수정한다.
3. 정규화·거리·유일성·시설 범위 기준을 테스트 사례로 고정한다. 새 정책 판단이 필요하면 구현 전에 보고한다.
4. 설계 결정 후 저장 모델·Repository 경계·마이그레이션·초기 적재 및 후보 생성 방식을 구현한다.
5. 개발자 검토 파일 내보내기·검토 결과 검증과 반영·중복 방지를 구현한다.
6. 저장된 연결을 이용한 검색·조회 보완과 출처 표현을 연결한다. 웹 노출 시 기존 고정 출처 문구의 최소 수정도 함께 수행한다.
7. 관련 테스트·Architecture·Static Analysis·Evaluation을 실행하고 실제 범위와 결과를 이 Evidence에 갱신한다.
8. 자체 검증 후 별도 Codex B 독립 리뷰를 기다린다. 실제 리뷰 결과와 개발자 최종 확인·승인 절차를 따른다.

이 순서는 전체 연결·조회 구현 계획이다. 후속 데이터 확보·저장 요청에서는 6.11절의 출처별 수집·저장 범위만 실행한다. 진행 중 추가 요구가 나오면 이 Task의 범위를 먼저 재검토하고, 후속 작업을 미리 확정하지 않는다.

### 6.8. 저장 구조 설계안과 현재 적용 범위

아래 5개는 독립 리뷰 APPROVE를 받은 설계 초안의 후보 구조다. 이후 데이터 확보·저장 지시에 따라 6.11절의 적재용 DDL을 적용했다. 대화 중 기본 3개는 출처별 정보 2개와 유효 연결 1개이며, 검토 이력·적재 결과 2개를 더해 현재 5개를 사용한다. 전체 연결 관리·검색 통합 설계가 확정·구현된 것으로 확대하지 않는다.

| 후보 테이블 | PK / 주요 참조·제약 | 책임과 주요 항목 |
|---|---|---|
| `tourapi_place` | PK `content_id`(외부 ID 문자열), FK `last_success_run_id` → `place_import_run.id` | TourAPI에서 확인한 필요한 항목, 지역·이름·주소·좌표, `data_version`, 마지막 성공 확인 시각. 연결 판정의 TourAPI 측 근거와 출처별 값 보존. |
| `busan_attraction` | PK `uc_seq`(외부 ID 문자열), FK `last_success_run_id` → `place_import_run.id` | 부산명소정보에서 확인한 필요한 항목, 지역·이름·주소·좌표, `data_version`, 마지막 성공 확인 시각. 부산 보완정보의 저장소. |
| `place_link` | PK/FK `content_id` → `tourapi_place.content_id`, `UNIQUE` + FK `uc_seq` → `busan_attraction.uc_seq` | 확정된 일대일 연결과 사용 상태, 자동/수동 방식, 양쪽 판정 대상 버전·근거·기준 버전·확인 시각, 동시 갱신 검사용 버전. 재검토 상태이면 보완 조회에서 제외. |
| `place_link_review` | PK `id`, 양쪽 외부 ID는 각 정보 테이블 FK, 인덱스 `(content_id, uc_seq, reviewed_at)` | 후보·승인·거절·재검토 이력. 판단 대상 버전·필요한 근거 값·주체·시각·사유 보존. 여러 후보를 저장할 수 있으며 유효 연결로 직접 사용하지 않음. |
| `place_import_run` | PK `id`, 인덱스 `(source, status, completed_at)` | 출처·수집 범위·시작/종료 시각·성공/실패·페이지/건수 검사 결과·마스킹된 실패 사유. 양쪽 전체 수집 완료 여부를 연결 판단 전에 확인. |

- 관계는 수집 실행 1:N 출처별 정보, TourAPI 장소 1:0..1 유효 연결, 부산 장소 1:0..1 유효 연결, 각 장소 1:N 검토 이력이다. 여러 후보·거절 이력을 `place_link`에 넣고 단일 UNIQUE 제약과 충돌시키지 않는다. 미연결은 유효 연결 행이 없는 상태로 표현할 수 있다.
- 확정 연결 저장과 해당 승인 이력 기록은 같은 트랜잭션으로 반영한다. DB의 일대일 제약과 응용 계층의 입력 버전·기존 연결 재검사를 함께 사용한다. 충돌 시 기존 연결을 덮어쓰지 않는다.
- 출처별 테이블에는 외부 응답 전체 JSON을 저장하지 않는다. 설명·연락처·홈페이지·이미지·운영정보 등 필요한 항목의 타입·길이·nullable 여부는 실제 API 응답과 컬럼 대응표로 결정한다. 제공되지 않는 필드나 없는 값은 생성하지 않는다.
- 항목별 수집 상태는 값과 구분한다. 정상 확인된 값 없음, 미요청, 수집 실패를 구분하고, 일부 API 성공으로 모든 필드의 확인 시각을 갱신하지 않는다. 복수 이미지·필드 상태를 별도 테이블로 분리할지는 응답 표본과 조회 요구를 확인한 뒤 설계안에 반영한다. 따라서 위 5개도 최종 테이블 수는 아니다.
- 초기 제안은 출처별 값을 보존하고 응용 서비스에서 표시값·출처·누락·충돌 상태를 산출하는 방식이다. 별도 통합 장소 테이블에 같은 표시값을 중복 저장할 필요성은 현재 확인되지 않았다. 표시값의 사전 저장이 필요해지면 무효화·재계산 기준을 포함해 별도 설계 판단을 받는다.
- 원본 근거가 갱신되어도 검토 당시의 버전과 필요한 근거 값은 이력에 보존한다. `data_version` 숫자만 남기고 판단 당시의 이름·주소·좌표를 복원할 수 없게 만들지 않는다.

#### 연결 해제·교체 상태 전이 제안

아래는 리뷰 권고를 구체화한 설계안이며 최종 상태 명칭·DDL과 함께 개발자가 확인한 뒤 구현한다.

| 전이 | 연결 행과 이력 처리 |
|---|---|
| 연결됨 → 재검토 필요 | 기존 `place_link` 행과 양쪽 유일 제약을 유지하고 부산 보완 사용만 중지한다. 중지 사유·대상 버전·근거를 이력으로 남긴다. 재검토 대기만으로 ID를 다른 연결에 할당하지 않는다. |
| 재검토 필요 → 기존 연결 재승인 | 기존 양쪽 ID·최신 데이터·예상 연결 버전을 다시 검증하고, 연결 상태 변경과 재승인 이력을 같은 트랜잭션으로 반영한다. |
| 연결됨/재검토 필요 → 명시적 연결 해제 | 개발자의 잘못된 연결 확정·해제 결정과 기존 행 버전을 검증한다. 이전 양쪽 ID·근거·방식·기준 버전·주체·시각·해제 사유를 `place_link_review`에 보존하고 `place_link` 행을 제거하는 작업을 같은 트랜잭션으로 처리한다. 출처별 정보와 과거 검토 이력은 삭제하지 않는다. |
| 기존 연결 → 승인된 새 연결로 교체 | 개발자의 명시적 교체 결정 후 기존 연결·새 후보의 양쪽 데이터 버전과 점유 상태를 재검증한다. 기존 연결 해제 이력, 기존 행 제거, 새 연결 생성과 승인 이력을 하나의 트랜잭션으로 반영한다. 새 대상이 다른 연결에 점유되어 있으면 거절하고 자동으로 그 연결까지 해제하지 않는다. |

- 해제·교체 후 이전 후보가 같은 근거로 자동 재연결되지 않도록 기존 거절 후보와 같은 재제안 방지 원칙을 적용한다. 근거가 달라지면 과거 결정을 보존하고 재검토한다.
- 별도 요청에서 해제된 ID를 재사용하려면 기존 연결 행 제거가 커밋되어야 한다. 위 교체 절차에서는 같은 트랜잭션 안에서 기존 행을 제거하고 새 연결을 생성한다. 이력은 `place_link`의 생존 여부에 종속시키지 않으며 연결 행 제거로 함께 삭제하지 않는다. 새 연결로 바뀌어도 기존 `tourapi-{contentid}`와 출처별 장소 정보는 유지한다.
- 동시 해제·교체·승인에서는 기존 행의 예상 버전 및 새 대상의 유일 제약을 검사한다. 충돌 또는 이력 기록 실패 시 전체 변경을 롤백한다. 작업 전 재검토로 중지된 연결은 실패 후에도 중지 상태를 유지한다. 구체 잠금 방식·일관된 잠금 순서는 구현 전 트랜잭션 설계에서 정한다.

### 6.9. 조회 기준 설계안 — 실시간 검색과 DB 조회 구분

기존 6.6절은 TourAPI 검색 결과에 DB의 연결·보완정보를 결합하는 흐름이다. 양쪽 출처 정보를 저장한다는 사실만으로 검색 기준을 DB로 전환한 것으로 취급하지 않는다. 다음 두 선택은 개발자 결정 대상이다.

| 선택 | 검색과 상세 조회 | 설계 영향 |
|---|---|---|
| A: 기존 검색 유지(현재 계획과 일치하는 제안) | TourAPI로 검색하고 반환된 `contentid` 목록으로 유효 연결·부산 정보를 DB에서 일괄 조회해 보완. 상세는 서버 조회 모델과 별도 계약을 먼저 설계. | TourAPI 저장은 우선 연결·검토와 출처별 값 보존 목적. 실시간 값과 저장값의 버전 차이 확인 필요. |
| B: DB 검색으로 전환 | 수집·공개가 완료된 TourAPI 저장 데이터를 기준으로 검색·페이지 처리하고, 연결표를 통해 부산 저장값을 함께 조회. 상세도 같은 공개 데이터 기준으로 구성. | 초기 수집 범위·검색/정렬/페이지 계약·새 장소 반영·수동 갱신 및 오래된 정보 표시 정책을 추가 결정해야 함. |

- 두 선택 모두 `tourapi-{contentid}`에서 `contentid`를 추출하고 `place_link.content_id`로 연결된 `uc_seq`를 얻은 뒤 `busan_attraction.uc_seq`로 부산 저장 데이터를 찾는다. 조회 시 이름·좌표로 재매칭하거나 매 요청 부산 API 전체를 호출하지 않는다.
- 유효 연결이 없어도 TourAPI 장소는 반환하며 부산 항목은 미확인으로 표시한다. 목록은 장소 ID 집합으로 일괄 조회하고 원래 결과 순서를 유지한다. 보완 저장소 장애는 실제 실패 상태로 구분한다.
- A를 선택하면 실시간 TourAPI 결과의 연결 근거와 승인 당시 근거가 호환되는지도 확인해야 한다. 기존 검색 응답 모델은 지역·연결 버전을 모두 갖고 있지 않으므로 응용 서비스 내부 메타데이터 계약을 먼저 정한다. 근거 변경·필요 근거 미확인은 해당 부산 보완 사용을 보류한다.
- 표시값의 단순 `COALESCE`만으로 항목 상태까지 확정하지 않는다. null 의미·수집 성공 여부·출처별 차이·연결 상태를 확인하고 응용 서비스에서 응답을 구성한다. 의미 일치 여부를 해석하지 못한 차이는 그대로 보존한다.
- 응답은 기존 검색 필드를 유지하면서 항목별 출처·마지막 확인 시각·미확인/충돌 및 보완 조회 실패를 표현할 위치를 정해야 한다. 구체 DTO·상세 경로와 웹 사용 방식은 미확정이며 구현 전에 확정한다. 진단 Port와 Rule의 기존 의미는 변경하지 않는다.

### 6.10. 적재·공개와 구현 착수 조건

- 초기 수집은 수동 실행을 전제로 한다. 전체 수집 완료 전 데이터는 후보 계산·현재 서비스 조회에서 제외한다. 최초 설계의 적재 격리 방식은 미정이었으나, 현재 출처별 적재는 6.11절의 메모리 수집 후 양쪽 일괄 트랜잭션 공개로 구현했다. 향후 전체 연결·조회 기능이나 수집 규모 확대에서 추가 테이블이 필요한지는 별도 검토한다.
- 실패한 수집으로 현재 공개된 출처별 값·기존 연결·마지막 성공 시각을 덮어쓰지 않는다. 성공한 새 데이터도 연결 근거가 바뀌면 관련 연결을 재검토 상태로 전환해 부산 보완 사용을 중지한다. 갱신과 연결 무효화는 조회 중 불일치가 생기지 않게 함께 공개한다.
- 구현 착수 전 산출물은 (1) 검색 기준 선택, (2) 필요한 출처별 API와 필드→컬럼 대응표, (3) 확정 ERD·PK/FK·유일 제약·인덱스·컬럼 타입, (4) 후보/검토/유효 연결 전환 및 근거 보존, (5) 적재 격리·공개·실패 시 보존 방식, (6) 검색·상세 응답 예시와 출처 표시, (7) 마이그레이션·검증 계획이다.
- 마이그레이션·저장소 검증은 H2 테스트와 별도로 서비스 대상 버전의 실제 MySQL 환경에서 수행할 계획이다. 격리된 테스트 DB에서 빈 스키마의 마이그레이션 및 기존 스키마에서의 적용, FK/UNIQUE 위반 거절, 연결 행 해제 후 이력 보존, 연결·이력 원자성 및 교체 실패 시 롤백을 확인한다. 실제 MySQL 버전·엔진·문자셋/콜레이션과 적용 도구는 DDL 확정 전에 기록한다.
- 실제 MySQL에서 독립된 트랜잭션/연결을 사용해 동일 TourAPI 또는 부산 ID에 대한 동시 승인, 승인과 해제·교체의 경쟁을 검증한다. 이중 유효 연결과 고아 이력이 생기지 않는지 확인한다. H2의 MySQL 호환 모드 통과를 실제 MySQL 검증으로 대체하지 않으며, MySQL 검증을 실행하지 못하면 미실행 사유를 Evidence에 기록하고 통과로 표시하지 않는다.
- 위 산출물의 정책 선택을 개발자가 확인한 뒤 구현한다. 이 문서의 기존 APPROVE와 커밋 승인을 새 저장·조회 설계나 데이터 적재 승인으로 확대하지 않는다.

### 6.11. 개발자 후속 요청 — 출처별 데이터 확보·DB 저장

2026-11-21 TourAPI `detailInfo2` 조회에서 정상 0건의 응답 본문은 `{"items":"","numOfRows":0,"pageNo":1,"totalCount":0}`, 결과 코드는 `0000`이었다. 수동 적재기는 결과 코드와 페이지를 검증한 뒤 총 0건이면 `items`가 정확히 빈 문자열인 경우만 수용한다. 그 밖의 구조는 수집 실패로 처리한다.

#### 실행 범위와 구현 전 확인

- 개발자가 “데이터 확보해서 db에 저장해줘”라고 지시했다. 이 새 지시를 출처별 데이터 수집·저장 구현과 실행의 근거로 삼는다. 검색 A/B 선택, 연결 정책 변경, Commit/Merge/Push 승인으로 확대하지 않는다.
- 구현 전에 현재 코드를 확인하고, 설정된 로컬 MySQL에 읽기 접속했다. MySQL **8.0.46**, 서버 `utf8mb4` / `utf8mb4_0900_ai_ci`이며 기존 `places`는 존재하지만 **0건**, `users`는 **2건**이었다. 코드에 없는 기존 일정 관련 테이블도 존재하므로 신규 5개 테이블만 추가하고 기존 테이블을 변경하지 않는다.
- 기존 Rule·Diagnosis Domain·Port·Rule Registry를 수정하지 않는다. 수집된 운영 문구를 해석하거나 PASS·방문 가능 판정으로 변환하지 않으며 타 지역 보완 적용도 수행하지 않는다. 연결 성공을 정보 확인 성공으로 간주하는 경로가 없다.
- 실제 응답 표본을 확인한 뒤 기술 선택을 보고했다. 기본 열과 필요한 항목만 선별한 `details JSON`, 항목별 상태/확인 시각/endpoint를 담은 `field_status JSON`으로 저장한다. 단일 응답의 이미지 2개는 별도 값으로 보존하고 외부 원본 응답 전체는 저장하지 않는다.
- 이 단계의 수집 데이터는 메모리에서 격리하고, 양쪽 전체 수집·페이지/ID/지역/응답 검증이 완료되어야 한 JDBC 트랜잭션으로 공개한다. 외부 호출 중 DB 데이터 트랜잭션을 유지하지 않는다. 적재 실행 행은 먼저 남기고 실패 시 정제된 실패 코드만 기록한다.

#### 실제 API·저장 필드 대응

| 출처 / API | 식별·범위 | 기본 열 또는 선별 부가정보 |
|---|---|---|
| TourAPI `KorService2/areaBasedList2` | `contentid`, `lDongRegnCd=26`, `contentTypeId=12` | 부산 관광지 전체 ID 집합과 페이지 완전성 확인. 반환된 ID의 상세를 조회하며 좌표가 없는 장소도 수집 건수에서 임의 제외하지 않음. |

- 출처는 테이블과 수집 실행의 `source`로 구분한다. 기본 열의 항목 상태도 `field_status`에 남긴다. `VALUE`(값 있음), `EMPTY`(응답의 빈 값), `MISSING`(필드 미제공), `INVALID`(유효하지 않은 좌표)를 구분한다. `무료`·`휴무 없음`·`상시 개방`을 빈 값으로 바꾸지 않는다. 확인 시각은 UTC이며 실제 최신성·방문일 적용 가능성을 보장하지 않는다.
- TourAPI 상세 endpoint와 부산 서비스는 실제 인증 요청의 응답 구조로 검증했다. 참고 공식 안내는 [TASK-010](TASK-010.md)의 두 제공기관 링크를 따른다. 인증키·비밀번호·전체 외부 응답은 Evidence나 Git에 기록하지 않는다.

#### 스키마·재실행·접근 경계

- 6.8절 후보 이름의 **5개 테이블**을 `ENGINE=InnoDB`, `utf8mb4_bin`으로 작성했다. 출처별 PK는 `VARCHAR(64)`, 이름 `VARCHAR(500)`, 주소 `VARCHAR(1000)`, 위경도 nullable `DOUBLE`, 시각 `DATETIME(6)`이다. 유효 연결 PK/FK와 부산 ID UNIQUE, 검토 이력의 출처별 FK를 두고 연결 삭제 cascade는 두지 않는다.
- 자동 서버 시작에 DDL/수집을 연결하지 않는다. 버전 SQL `db/manual/TASK016-V1-place-import.sql`을 opt-in 명령에서만 적용한다. `CREATE TABLE IF NOT EXISTS`의 재적용을 실제 MySQL에서 검증하며, MySQL DDL은 데이터 공개 트랜잭션과 별도다. 향후 구조 변경은 새 버전 SQL로 검토한다.
- 기존 출처 ID를 upsert하며 내용 해시와 연결 근거 해시를 저장한다. 값이 동일하면 `data_version`은 유지하고 정상 확인 시각·수집 실행 참조만 갱신한다. 해시에는 관측 시각과 JSON 객체 키 순서가 영향을 주지 않도록 한다. 목록에서 사라진 장소를 자동 삭제하거나 폐업 처리하지 않는다.
- 수집 실행 간 MySQL 이름 잠금으로 동시 적재를 막는다. 이미 연결된 장소의 이름·주소·좌표·지역이 달라지는 경우 출처 데이터 공개와 함께 연결을 `REVIEW_REQUIRED`로 바꾸고 과거 근거를 이력에 보존한다. 현재 적재에서는 연결/승인/후보 행을 새로 생성하지 않는다.
