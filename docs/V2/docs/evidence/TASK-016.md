## 2. Goal

기존 TourAPI 관광지와 동일한 부산명소정보를 연결하고, 부족한 정보를 출처와 함께 저장·조회하는 구현 계획을 정리한다.

## 6. Codex A 주요 판단

### 6.1. 기존 구조 확인

- 현재 `/api/places/search`는 `PlaceController`에서 `TourApiClient`를 직접 호출한다.
- 현재 `PlaceSearchResult`에는 장소 ID·이름·주소·분류·좌표·이미지·기존 체류시간 필드가 있다. 보완정보와 출처를 모두 표현하는 상세 조회 계약은 별도 설계가 필요하다.
- 진단의 `TourismPort.findPlace`는 현재 `TourApiTourismAdapter`를 통해 장소 이름·좌표·지역을 조회한다. 운영정보를 저장했다고 기존 운영시간 미지원 상태를 해제하지 않는다.
- 향후 검색·조회 응용 서비스에서 저장된 보완정보를 결합하고, 외부 DTO와 JPA 모델을 Diagnosis Domain으로 직접 전달하지 않는다.

### 6.2. 자동 연결 기준

다음 조건을 모두 만족할 때만 자동 연결한다.

| 항목 | 기준 |
|---|---|
| 지역 | 양쪽 모두 부산으로 확인되어야 한다. 이름에 부산이 포함된다는 이유로 지역을 추정하지 않는다. |
| 이름 | 공백·단순 구두점 정리 후 일치해야 한다. 본점·분관·입구·전망대 등 식별 의미를 가진 단어는 보존한다. |
| 주소 | 동일 체계의 도로명·건물번호 또는 지번이 일치해야 한다. 도로명과 지번 간 대응을 확인하지 못하면 일치로 추정하지 않는다. |
| 좌표 | 유효한 위경도 간 지표면 거리가 100m 이하여야 한다. |
| 유일성 | 양쪽에서 서로 유일한 적격 연결 대상이어야 하며, 기존 유효 연결과 충돌하지 않아야 한다. |
| 시설 범위 | 관광지 전체와 내부 시설, 입구 등 서로 다른 대상을 합치지 않는다. 동일 범위를 확인할 수 없으면 검토 대상으로 남긴다. |

- 이름 정규화가 괄호 안 시설명 등 의미 있는 내용을 제거하지 않도록 한다. 구체적인 정규화 목록과 경계 사례는 구현 시 테스트로 고정한다.
- 주소·좌표 누락, 이름 차이, 복수 후보, 다른 시설 범위 또는 100m 초과는 자동 연결하지 않는다.
- 100m는 초기 자동 연결 상한이다. 넓은 관광지의 좌표 차이는 개발자가 별도로 확인할 수 있다. 실제 표본에서 기준 변경이 필요하면 근거를 보고하고 개발자 결정 후 변경한다.
- 후보 탐색과 자동 연결을 구분한다. 후보 검색의 거리·유사도만으로 연결을 승인하지 않으며, 실제 데이터 표본을 확인한 뒤 후보 검색 방식의 세부값을 정한다.
- 초기에는 양쪽 ID 간 일대일 연결을 원칙으로 한다. 다대일·일대다 사례가 나오면 별도 판단 대상으로 보고한다.

### 6.3. 개발자 검토와 연결 상태

- 검토 파일에는 양쪽 ID·이름·주소·좌표·거리, 자동 연결하지 않은 사유와 기존 연결 유무를 포함한다.
- 초기에는 별도 관리자 UI 없이 파일로 후보를 내보내고 개발자가 승인·거절한 결과를 검증 후 반영하는 방식을 사용한다.
- 검토 결과 반영 시 대상 ID·입력 데이터 버전·기존 연결을 다시 확인한다. 오래된 검토 결과로 바뀐 장소를 연결하거나 기존 연결을 덮어쓰지 않는다.
- 연결 상태는 미연결·검토 대기·연결됨·거절·재검토 필요를 구분한다. 명칭과 실제 저장 형식은 구현 시 확정한다.
- 자동/수동 연결 구분, 판단 근거, 기준 버전, 확인 시각과 검토 주체를 기록한다.
- 거절한 후보는 이름·주소·좌표 등 연결 근거가 그대로라면 반복 제안하지 않는다. 근거가 바뀌면 이전 판단을 보존하고 재검토 대상으로 분리한다.
- 연결 근거의 의미 있는 변경을 발견하면 임의로 새 장소에 재연결하지 않는다. 해당 연결의 부산 보완정보 사용을 중지하고 개발자에게 재확인을 요청한다. 변경 감지의 세부 기준은 구현 전 표본으로 구체화한다.
- 연결이 없거나 검토 중이어도 기존 TourAPI 검색·일정 구성을 사용할 수 있다. 부산 보완정보 미확인을 장소 부재로 처리하지 않는다.

### 6.4. 정보 보완과 충돌

| 상태 | 조회·저장 원칙 |
|---|---|
| TourAPI에 유효한 값이 있음 | 기본 표시값으로 유지한다. |
| TourAPI 값이 비고 부산 값이 있음 | 확인된 연결에 한해 부산 값으로 보완하고 출처를 표시한다. |
| 양쪽 값이 같거나 의미가 같음을 확인함 | 출처별 값을 보존하고 일치 근거를 남긴다. |
| 서로 다른 의미이거나 동일 의미 여부가 불명확함 | 양쪽 값과 차이·확인 상태를 보존한다. 임의로 진단 근거를 확정하지 않는다. |
| 양쪽 모두 값이 없음 | 미확인으로 유지한다. |

- 수집 대상은 운영일·휴무일·운영시간·요금·설명·연락처·홈페이지·교통정보·편의시설·이미지 등 서비스에 필요한 정보다. 제공되지 않는 항목은 추정 생성하지 않는다.
- null·빈 문자열·공백은 값 없음으로 정리한다. `무료`, `휴무 없음`, `상시 개방`처럼 의미가 있는 값을 빈 값으로 제거하지 않는다. 표현을 해석할 수 있다는 것과 진단에 적용할 수 있다는 것은 구분한다.
- 문구를 억지로 요약하거나 합쳐 새로운 운영시간을 만들지 않는다. 예를 들어 TourAPI `09:00~18:00`와 부산 `10:00~17:00`를 `09:00~17:00`로 합치지 않는다.
- 운영정보의 차이가 해결되지 않으면 영향을 받는 조건은 검증 불가로 유지한다. 충돌의 상세 해소와 운영시간 평가 구현은 이번 범위 밖이다.
- 장소 연결 성공만으로 모든 항목을 확인됨으로 표시하지 않는다. 부산에서만 보완된 이미지 등을 TourAPI 출처로 표시하지 않는다.

### 6.5. 저장 개념과 실패 처리

구체적인 테이블명·컬럼·인덱스·마이그레이션은 구현 시작 시 기존 저장 구조와 실제 응답 표본을 확인한 뒤 설계한다. 필요한 저장 개념은 다음과 같다.

| 개념 | 저장할 내용 |
|---|---|
| 출처별 장소 정보 | 제공기관·외부 ID·이름·주소·좌표·확인된 지역 및 서비스용 정보 |
| 장소 연결 | 공통 장소 ID·부산 콘텐츠 ID·연결 상태·방식·근거·기준 버전 |
| 항목별 보완정보 | 출처별 값·선택한 표시값과 출처·누락 및 충돌 상태 |
| 확인 시각 | 마지막 정상 수집 확인 시각, 제공기관 수정 시각이 있으면 별도 보관 |
| 검토 이력 | 승인·거절·재검토의 근거·주체·시각·판단 대상 버전 |
| 적재 결과 | 실행 식별자·성공/실패·처리 건수와 마스킹한 실패 사유 |

- 외부 API 응답 전체를 무분별하게 저장하지 않는다. 선택한 항목의 출처별 원문 값과 판단 근거를 필요한 범위에서 보존한다.
- 동일 데이터를 다시 반영해도 연결·보완정보가 중복 생성되지 않게 한다. 잘못된 중복 연결은 저장 제약과 응용 계층 양쪽에서 막는다.
- 최초 적재는 수동 실행을 전제로 한다. 전체 수집이 필요한 작업에서는 페이지 누락·중복·실패 여부를 확인한 뒤 정상 수집 단위를 반영한다. 중간 실패를 완전한 빈 결과로 간주하지 않는다.
- 조회·수집 실패 시 기존 데이터와 마지막 정상 확인 시각을 보존하고 실패 사실을 구분한다. 성공하지 않은 요청으로 확인 시각을 갱신하지 않는다.
- 정상 응답에서 특정 값의 부재가 확인된 경우와 통신·파싱 실패로 값을 모르는 경우를 구분한다. 이전 값만으로 현재 항목을 확인됨으로 표시하지 않는다.
- 목록에서 한 번 보이지 않았다는 이유로 장소를 삭제하거나 폐업으로 판단하지 않는다. 삭제·ID 변경의 상세 운영 정책은 발견 사례를 보고 별도로 정한다.
- 수집 확인 시각은 현장 정보의 정확성이나 방문일 적용 가능성을 보장하지 않는다. 이번 계획에서는 정보 사용 기한을 새로 확정하지 않는다.

### 6.6. 조회 흐름과 경계

1. 기존 TourAPI 검색으로 장소 목록과 공통 장소 ID를 얻는다.
2. 결과의 ID 목록으로 저장된 유효 연결·보완정보를 일괄 조회한다. 장소마다 DB 조회를 반복하는 구조를 피한다.
3. 항목별 보완 기준에 따라 응답을 구성하고 출처·미확인·충돌 상태를 표현한다.
4. 상세 용도의 정보는 별도 조회 모델로 제공할 수 있게 설계한다. 기존 검색의 ID·순서·페이지 동작을 임의로 바꾸지 않는다.
5. 진단 연결에 필요한 정보는 Port 뒤에서 내부 모델로 변환한다. 저장된 운영정보가 생겼다는 이유로 미구현 Rule을 PASS로 바꾸지 않는다.

- 부산 데이터 변환은 부산 Adapter에, 저장 접근은 Repository 경계에 둔다. 장소 연결·보완 조회는 장소 관리 책임으로 구성한다.
