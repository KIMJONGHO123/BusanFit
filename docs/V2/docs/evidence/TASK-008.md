# TASK-008 Evidence

상태: **완료 — Codex B 독립 리뷰 APPROVE 및 개발자 최종 확인 완료**.
작업일: 2026-10-25. 진단 규칙의 사전 검토와 개발자 결정 기록이며, 진단 엔진 구현 또는 공통 명세 수정 완료를 뜻하지 않는다.

## 1. Task ID

`TASK-008`

## 2. Goal

진단 로직 구현 전에 기존 규칙의 판단 공백과 모호한 조건을 검토하고, 개발자가 정한 범위 제한을 기록한다. 확인된 근거로 판단하고 확인하지 못한 부분을 사용자에게 명시하는 기존 원칙을 유지한다.

## 3. 관련 요구사항

- 개발자가 진단 로직 구현에 앞서 기존 일정 진단 규칙의 문제 여부를 검토하도록 요청함.
- 검토 범위를 지나치게 확장하지 않음. 복잡한 운영시간 예외나 외부 데이터의 불명확한 적용 범위를 모두 해결하는 기능을 요구하지 않음.
- 지원하지 못하거나 해석할 근거가 부족한 경우, 영향을 받는 평가 항목을 `UNVERIFIABLE`로 처리하고 이유를 표시하는 방향으로 정리함.
- 확인 가능한 다른 항목의 평가는 계속하고, 확인된 조정 필요 결과는 유지함.
- 이번 변경은 Evidence 작성에 한정함. 코드, 공통 명세, Evaluation Set은 수정하지 않음.
- 기존에 승인된 Evidence와 작업 시작 전 존재한 모바일·architecture 문서 수정은 보존함.

## 6. Codex A 주요 판단

### 구현 방식

- 실행 코드는 구현하지 않음. 규칙·불변조건·공통 계약·Evaluation 문서를 대조하고 구체적인 일정 사례를 대입해 검토함.
- 최초 사전 검토 결론은 **CHANGES_REQUIRED(구현 전 명세 보완 필요)**였음. 이는 Codex A의 검토 의견이며 Codex B 공식 리뷰 결과가 아님.
- 이후 개발자가 과도한 범위 확장을 금지하고, 지원하지 못하는 경우를 명시적 검증 불가로 처리하도록 방향을 정함. 아래 검토 사항은 해당 범위 제한을 반영한 보완 방향임.

### 기존 구조와의 관계

- 일정 판정과 검증 상태의 분리, 확인된 조정 필요 우선, 최종 체류시간 중복 합산 금지, 지역 Scope 격리 원칙은 유지함.
- `POSSIBLE + PARTIAL`은 시간상 계산이 완료됐지만 일부 항목을 확인하지 못한 경우 허용됨. 이를 전체 일정의 안전 보장으로 해석하지 않음.
- `UNVERIFIABLE`은 대상별 Rule 평가 상태임. 이것만으로 일정 전체를 `UNDETERMINED`로 바꾸지 않으며, 최종 decision과 verificationStatus는 기존 계약에 따라 별도로 집계함.
- 미지원·확인 불가를 `PASS` 또는 `NOT_APPLICABLE`로 숨기지 않고, RuleResult와 coverage에 해당 이유를 표시하는 기존 방향을 유지함.
- Diagnosis Domain, RuleRegistry, Port/Adapter의 책임 변경은 없음.

### 검토에서 발견한 보완 사항

#### 1. 이동시간 미확인 중에도 증명 가능한 시간 초과

- 위치: 공통 계약 4절 시간 계산, 6절 판정 집계.
- 사례: 여행 가능 시간이 3시간인데 요청한 최종 체류시간 합계만 4시간이고 이동시간은 확인하지 못함.
- 문제: 이동시간 미확인을 이유로 전체 시간 판단을 중단하면 이미 증명 가능한 초과까지 `UNDETERMINED`로 남길 수 있음. 해당 사례의 명시적 규칙·검증 사례가 부족함.
- 보완 방향: 확인된 체류시간 합계만으로도 초과가 증명되면 `ADJUSTMENT_REQUIRED`를 유지함. 미확인 이동시간을 0초로 확정하거나 정확한 총 필요시간·잔여시간을 생성하지 않음.
- 관련 원칙: INV-004, INV-009. 확인된 조정 필요가 미확인 정보 때문에 사라지지 않아야 함.

#### 2. 기본 권장시간과 활동시간의 포함 범위

- 위치: 공통 계약 3절 권장 총시간 산정.
- 사례: 공원의 기본 권장시간에 산책이 이미 포함됐는지 모르는데 산책 활동시간을 추가 합산함.
- 문제: 서버 일정 합산에서 중복을 막더라도 권장 총시간 비교에서 중복 계산해 불필요한 부족 경고를 만들 수 있음.
- 보완 방향: 기본 권장시간의 근거와 활동 포함 범위가 불명확하면 임의 합산하지 않고 해당 권장시간 비교를 `UNVERIFIABLE`로 남김. 최종 `plannedStaySeconds`를 이용한 일정 계산은 계속함.
- 범위 제한: 모든 장소의 활동 포함 관계를 새로 구축하거나 권장시간을 임의 추정하지 않음. 기존 웹의 근거 없는 기본 권장시간 미사용 방침을 유지함.
- 관련 원칙: INV-001, INV-004, INV-008.

#### 3. 복잡한 운영시간 조건

- 위치: Rules의 운영시간 항목, 공통 계약 4·6절.
- 사례: 입장 마감, 휴게시간, 여러 운영 구간 또는 개장 전 대기 여부를 해석해야 하는 방문.
- 문제: 운영시간의 일부만 해석해 `PASS`나 조정 필요를 단정하면 실제 근거보다 강한 판단이 될 수 있음.
- 보완 방향: 지원하고 명확히 해석할 수 있는 정보로만 평가함. 방문 가능 여부를 판단하는 데 필요한 조건을 지원하지 못하면 영향을 받는 운영시간 평가를 `UNVERIFIABLE`로 기록하고 원인을 표시함.
- 범위 제한: 복잡한 운영시간 파서, 개장까지 자동 대기, 운영시간에 맞춘 일정 재배치 등을 이번 보완의 필수 기능으로 추가하지 않음. 구체적인 지원 형식과 경계 비교 기준은 해당 Rule 구현 전 정리할 항목으로 남김.
- 관련 원칙: INV-001, INV-004, INV-005.

#### 4. 외부 데이터의 적용 날짜·대상

- 위치: 공통 계약 5절 dataReferences, 6절 공식 통제 판정.
- 사례: 오늘의 통제 정보가 다음 달 여행에도 적용되는지 확인할 수 없음.
- 문제: API 호출 성공만으로 여행 날짜와 대상에 유효한 근거라고 취급하면 잘못된 정상·조정 필요 판정을 만들 수 있음.
- 보완 방향: 필요한 적용 날짜·대상 범위를 확인하지 못하면 해당 평가를 `UNVERIFIABLE`로 기록함. 확인된 근거의 출처·기준시각과 확인하지 못한 이유를 구분함.
- 범위 제한: 모든 외부 데이터의 유효기간·갱신주기·상충 정보 해결 정책을 지금 정의하지 않음. 구체적인 데이터별 지원 조건은 Adapter와 해당 Rule 작업에서 정함.
- 관련 원칙: INV-001, INV-002, INV-004. CRITICAL 판정도 해당 일정에 적용되는 통제가 확인된 근거를 필요로 함.

#### 5. 경로 확인 실패와 이동 불가의 구분

- 위치: 공통 계약 7절 외부 실패 처리, TravelTimePort 경계.
- 사례: 통신 장애, 빈 경로 응답, 선택 이동수단의 이동 불가가 같은 상태로 취급될 수 있음.
- 문제: 빈 응답을 이동 불가로 확정하거나, 미확인 이동을 가능하다고 가정할 여지가 있음.
- 보완 방향: 응답 의미가 불명확하거나 이동 가능 여부를 확인하지 못하면 해당 평가를 `UNVERIFIABLE`로 남김. 시간상 필수 데이터가 부족하고 확인된 조정 필요가 없으면 기존 계약대로 `UNDETERMINED`를 사용함.
- 범위 제한: 이번 기록에서 새로운 이동 불가 판정 정책을 확정하지 않음. 명확한 이동 불가 응답의 인정 조건과 결과는 실제 Adapter 계약을 확인하는 후속 작업에서 결정함.
- 관련 원칙: INV-001, INV-004, INV-009.

### 후속 명세 반영 시 권고한 경계

- 운영시간 일부를 해석하지 못해도 독립적으로 확인된 위반은 유지함. 방문일 휴무가 확정됐다면 휴게시간 해석 실패 때문에 확인된 `ADJUSTMENT_REQUIRED`를 지우지 않음. 해석하지 못한 조건은 별도로 드러내며, 구체적인 평가 분해는 후속 명세에서 정리함.

- 위 두 경계는 리뷰어가 현재 승인을 막는 문제가 아닌 후속 명세 반영 권고로 명시함.
