## 6. Codex A 주요 판단

### 구현 방식

- 작업 시작 시 MySQL(3306), Spring Boot(8080), Vite(5173)가 실행 중이고 기존 비공개 설정에 키가 있음을 값 노출 없이 확인함. 앞선 TASK-006/007의 환경 미가동 기록과 현재 상태를 구분함.
- 서버 직접 호출과 웹 프록시 호출에서 실제 TourAPI ID·한글 이름·주소·좌표·사진 URL을 확인함. 이후 수정한 클래스로 서버를 재시작하고 실제 API 브라우저 검증을 수행함.
- 서버의 성공 코드 `0000`과 응답 구조를 확인해야 빈 결과를 반환하도록 변경함. HTTP 실패·API 오류·잘못된 JSON/XML·누락된 헤더/body/totalCount/items·잘못된 items 구조는 실패로 구분함.
- 정상 빈 items 문자열, totalCount 0의 빈 객체/null item, 빈 item 배열은 빈 결과로 처리함. 전체 건수가 양수여도 마지막 페이지 이후에는 빈 페이지가 가능하므로 정상 빈 items 문자열은 허용함.
- 기존 ID·이름·좌표 누락 항목 필터링을 유지하고 NaN/Infinity·좌표 범위 초과를 추가로 제외함. 좌표를 임의로 채우지 않음.
- 키와 쿼검색어는 URI 변수 값으로 인코딩함. 한글 및 `&`, `+`, `/`, `=`가 리 구조를 바꾸지 않는지 확인함.
- 외부 오류 메시지·본문은 사용자 응답에 그대로 포함하지 않음. 실제 인증키 파일은 수정하지 않음.
- 실제 API 검증은 환경 변수로 명시적으로 활성화하며 제품 코드에 mock/fallback을 추가하지 않음.

### 기존 구조와의 관계 / 구현 전 검증

- Rule 의미·선택·지역 Scope·집계 정책 변경 없음. 검색의 부산·관광지 필터를 유지함.
- 부산이라는 서비스 범위는 유지하고 외부 API에서 그 범위를 지정하는 파라미터만 현행 법정동 코드로 교체함. Domain의 지역코드 정책이나 전국 검색 확장이 아님. 관광지 분류 `contentTypeId=12`도 유지함.
- 기존 검색 Adapter와 내부 `PlaceSearchResult` 변환 경계에서만 보완함. V2 Diagnosis Domain은 아직 구현하지 않았으며 외부 DTO를 Domain으로 전달하는 코드도 추가하지 않음. TourismPort 정의·진단 연결은 후속 범위임.
- INV-001/004: 확인 실패를 정상 빈 결과로 숨기지 않고, 유효한 좌표 없는 항목을 진단 가능한 장소처럼 만들지 않음.
- INV-002/003/008/009: 진단 코드·RuleRegistry·시간 계산·지역 판정은 변경하지 않음.
- INV-005: 운영시간·권장시간 미확인 표시와 진단 미구현 안내 유지. 입력 확인 성공을 진단 성공으로 표시하지 않음.
- INV-006: 외부 원본 응답 저장 추가 없음. 테스트 첨부는 내부 변환 결과 중 선택 장소와 성공 상태의 최소 요약 및 화면 캡처임.
- INV-007: 새로운 진단 정책 결정 없음. 개발자가 승인한 검색 연동 검증 범위에서 진행함.

### 구현 중 발견한 문제 / 한계

- 기존 파서는 성공 코드·응답 구조가 없거나 일부 구조가 잘못돼도 빈 배열을 반환할 수 있었음. 성공·빈 결과·실패를 분리하도록 보완함.
- 초기 실제 API 테스트는 React StrictMode가 취소한 첫 활동 정책 요청 본문을 읽어 실패함(PC/모바일 각 1건). 테스트가 `response.finished()`로 정상 완료된 요청만 선택하도록 수정하고 실제 4건을 재실행해 모두 통과함. 제품 동작 수정은 필요하지 않았음.
- PowerShell 5의 응답 문자열 디코딩과 Node stdin 한글 전달 때문에 탐색 출력이 깨지거나 검색어가 변형되는 경우가 있었음. Node의 Unicode escape 검색어와 UTF-8 JSON 읽기로 실제 응답의 정상 한글을 재확인함. 브라우저에서도 정상 한글 확인함.
- 기존 검색 DTO의 `estimatedStayMinutes: 90`은 근거 없는 레거시 값이며 현재 웹은 무시함. 호환성을 위해 계약은 유지함. 장소별 권장시간으로 검증·표시하거나 진단에 적용하지 않음.
- 현재 상세 화면은 검색 응답 정보만 표시함. 운영시간/권장시간과 검색 ID의 진단 연결은 미구현이며 기존 진단은 하드코딩 목록을 사용함.

### 개발자 후속 제보에 따른 지역 필터 교정

- 초기 성공 검증은 실제 API를 사용했으나, 기존 부산 필터의 명세 폐기 안내와 대표 장소 누락을 놓침. 초기 4건 통과는 지역 검색 완전성을 검증한 결과가 아님.
- 개발자가 감천문화마을 미검색·6페이지 제한을 제보하고 공식 `/areaCode2`의 미사용·삭제 예정 안내를 고려해 재확인하도록 지시함. 당시에는 독립 Codex B 결과를 전달받지 않았으며, 이후 수신한 실제 리뷰 결과는 10절에 별도로 기록함.
- 공공데이터포털 공식 페이지의 내장 Swagger를 직접 읽어 `/areaCode2` 설명이 `미사용 기능 (삭제예정-법정동 시도코드 대체)`임을 확인함. 대체 `/ldongCode2`는 법정동 시도·시군구 코드 조회 기능임.
- 실제 `/ldongCode2` 조회에서 `{code: "26", name: "부산광역시"}`를 확인함. 같은 KorService2의 검색·목록 API는 유지하고 지역 파라미터만 `lDongRegnCd=26`으로 교체함. 폐기 예정 API를 매 검색마다 호출하는 구현은 추가하지 않음.
- 원본 비교: `areaCode=6 + contentTypeId=12`는 113건이고 감천문화마을 미조회. `lDongRegnCd=26 + contentTypeId=12`는 351건이며 `부산 감천문화마을(contentid=1997221)` 조회됨. 해당 항목의 기존 `areacode`는 빈 문자열, `lDongRegnCd`는 `26`임.
- 교체 후 원본 API에서 351개 고유 ID를 모두 조회하여 법정동 지역코드가 전부 `26`임을 확인함. 전국 검색 후 이름·주소로 부산을 추정하는 방식이 아님.
- 수정된 실행 서버의 웹 프록시에서 감천문화마을 1건, 목록 7페이지 20건, 18페이지 11건, 19페이지 0건을 확인함. 수치는 작업 시점의 TourAPI 등록 건수이며 지역의 모든 실제 장소 수나 영구 고정값이 아님.
- 웹 배열 계약에는 전체 건수가 없고 유효하지 않은 좌표 항목이 제외될 수 있으므로 전체 페이지를 확정해 표시하는 UI는 추가하지 않음.

### 합의된 후속 계획 — 부산명소정보 보완·DB 조회·주기적 갱신(미구현)

기존 TourAPI 관광지 정보를 기본으로 유지하고, 동일한 관광지로 확인된 부산명소정보를 연결하여 부족한 정보를 폭넓게 보완한다. 개발자는 후속 대화에서 **주 1회 갱신 + TourAPI의 빈 정보를 부산명소정보로 최대한 보완 + 통합된 정보에서 용도별 조회** 방향에 동의하고 본 문서에 추가하도록 지시했다. 이번 변경은 계획의 문서 기록까지이며 실행 코드·DB 스키마·스케줄러 구현은 포함하지 않는다.

1. **같은 관광지인지 확인한다.** 같은 부산 지역이라는 이유만으로 합치지 않는다. 이름·주소·좌표 등을 비교하여 동일 장소인지 확인하고, 확신할 수 없는 항목은 연결하지 않는다.
2. **기존 장소 ID를 유지하고 보완 정보를 폭넓게 저장한다.** 사용자에게 제공하는 기존 `tourapi-{contentid}` ID를 유지하고 `TourAPI contentid ↔ 부산명소 UC_SEQ` 연결을 보관한다. 수집·저장 대상은 운영일·휴무일·운영시간·요금에 한정하지 않고, 설명·연락처·홈페이지·교통정보·편의시설·이미지 등 서비스에서 활용할 수 있는 정보까지 포함한다. 필요한 항목을 출처별로 정리하고 마지막 확인 시각을 함께 저장한다. 현재 진단에 사용하지 않는다는 이유만으로 화면·후속 기능에서 활용할 정보를 제외하지 않되, 외부 API 원본 응답 전체를 무분별하게 저장하지 않는다.
3. **TourAPI의 빈 정보를 보완하고 출처를 보존한다.** TourAPI에 값이 있으면 기본값으로 유지하고, 값이 없으면 부산명소정보에 있는 값으로 보완한다. 두 출처의 값이 다르면 양쪽 값과 출처를 보관하며, 서로 보완되는 정보와 의미가 충돌하는 정보를 구분한다. 운영정보가 충돌하면 기본 표시값의 선택만으로 진단 근거까지 확정하지 않으며, 충돌 처리 정책이 확정되기 전에는 영향을 받는 평가를 검증 불가로 남긴다. 두 출처 모두 값이 없으면 미확인으로 유지한다. 선택 항목이라는 이유로 수집 범위를 줄이지 않으며, 장소 연결 성공을 모든 항목의 확인 성공으로 간주하지 않는다.
4. **통합된 정보에서 용도별로 조회한다.** 저장된 장소 연결과 보완 정보를 기존 TourAPI 검색 결과에 결합하여 하나의 관광지 응답으로 제공한다. 검색·상세 화면에서는 소개·사진·연락처·교통·편의시설 정보를, 진단에서는 운영일·휴무일·운영시간 등 필요한 정보를 선택해 사용한다. 근거에는 사용한 출처와 마지막 확인 시각을 표시한다. 화면을 열 때마다 두 API 전체를 다시 수집하거나 같은 관광지를 찾는 비교 작업을 반복하지 않는다. 사용자가 입력한 활동·최종 체류시간은 외부 정보로 덮어쓰지 않으며, 근거 없는 권장 체류시간도 생성하지 않는다.
5. **부산명소정보는 초기 주 1회 갱신한다.** 매일 전체 수집하는 대신 주 1회 수집으로 시작하고 실제 정보 변경 빈도와 운영 비용을 확인하여 주기를 조정한다. 서버가 부산명소 API를 다시 조회하여 연결된 장소의 보완 정보 변경 사항을 반영한다. 새 장소나 ID 변경으로 기존 연결을 사용할 수 없는 항목은 같은 장소인지 다시 확인한 뒤 연결하며 임의로 기존 ID에 덮어쓰지 않는다. 구체적인 실행 요일·시각과 재시도 방식은 후속 구현 전에 정한다.
6. **갱신 실패와 정보의 적용 가능성을 구분한다.** 갱신에 실패하면 기존 정보를 최신 정보처럼 취급하거나 마지막 성공 확인 시각을 성공한 것처럼 갱신하지 않는다. 필요한 정보를 보존할 수 있더라도 마지막 확인 시각과 갱신 실패 상태를 구분한다. 조회 성공은 제공기관 정보의 실제 최신성이나 방문일 적용 가능성을 보장하지 않는다. 앞선 대화에서 제안했던 매일 수집·7일 경과 시 일괄 사용 중단은 채택하지 않는다. 데이터별 최신성·진단 사용 기준은 별도로 정하며, 정보가 오래되었거나 방문일에 적용 가능한지 확인할 수 없으면 관련 진단을 검증 불가로 남기고 정상·안전으로 간주하지 않는다.

아직 확정하지 않은 구현·정책 기준:

- 동일 장소 자동 연결 기준과 애매한 후보의 확인 절차.
- 주 1회 갱신의 실행 요일·시각, 데이터별 최신성·진단 사용 기준, 재시도 방식, 신규·변경·삭제 항목의 연결 처리 기준.
- 두 출처의 운영정보가 충돌할 때의 상세 처리·해소 기준. 기본 표시값을 TourAPI로 유지하더라도 임의로 한쪽을 올바른 진단 근거로 확정하지 않는다.
- 구체적인 DB 스키마와 조회·갱신 구현. 외부 호출·응답 변환은 Adapter, 저장 접근은 Repository 경계로 분리하며 외부 DTO를 Diagnosis Domain에 직접 전달하지 않는다.

위 미정 기준은 후속 구현 전에 개발자와 확정한다. 부산명소정보에만 있는 장소의 검색 목록 추가와 TourAPI 기본정보의 주기적 동기화는 이번 정보 보완 계획의 구현 범위에 포함하지 않고 후속 검토한다. 개발자와의 후속 대화에서 구현 순서를 **진단 엔진·웹 결과 연결 먼저 → 두 API의 장소 연결·DB 저장·주기적 갱신을 통한 명소정보 보완**으로 조정함. 운영정보 미확인 상태는 엔진에서 검증 불가로 표현한다. 침수·하천 수위·축제·주차장 등 나머지 API는 배포·운영 단계에서 후속 검토한다.
