# Diagnosis Rule Specification

## 1. 기본 인터페이스 개념

```text
DiagnosisRule
 ├─ Rule ID
 ├─ Scope
 │   ├─ NATIONAL
 │   └─ REGION
 │       └─ Region Code
 ├─ Importance
 │   ├─ NORMAL
 │   ├─ IMPORTANT
 │   └─ CRITICAL
 └─ evaluate(DiagnosisContext)
      ↓
    RuleResult
```

구현 언어와 구체 타입은 실제 코드 단계에서 정하되, 위 의미 구조는 유지한다.

## 2. 전국 공통 Rule

### 이동시간

질문:

> 현재 일정 종료 후 이동했을 때 다음 일정 시작 전에 도착 가능한가?

필요 데이터 예:

- 앞 일정 종료 시각
- 다음 일정 시작 시각
- 이동시간
- 출발/도착 좌표

통신 실패나 의미가 불명확한 빈 경로 응답만으로 이동 가능 또는 이동 불가를 확정하지 않는다.
해당 구간은 UNVERIFIABLE로 기록하고, 시간상 필수 데이터가 부족하며 독립적으로 확인된 조정 필요가 없다면 최종 판정은 UNDETERMINED이다.
명확한 이동 불가 응답의 인정 조건과 판정은 실제 Adapter 계약을 확인하는 별도 정책 작업에서 정한다.
기존 계약이 허용한 TMAP 조회 시점의 예상시간은 시간 계산에 사용할 수 있으나 미래 출발시각의 예측으로 표현하지 않는다.

### 체류시간

질문:

> 해당 장소에서 필요한 체류시간을 확보했는가?

기본 권장시간과 선택 활동시간은 서로 중복되지 않는다는 근거가 있을 때만 합산한다.
기본 권장시간의 근거나 활동 포함 범위가 불명확하면 해당 권장 총시간 비교를 UNVERIFIABLE로 기록한다.
이를 이유로 사용자가 확정한 plannedStaySeconds를 변경하거나 최종 체류시간을 이용한 다른 일정 계산을 중단하지 않는다.

### 운영시간

질문:

> 방문 예정 시간에 시설이 운영되는가?

운영시간을 확인할 수 없는 경우 임의로 영업 중으로 가정하지 않는다.

지원하고 명확히 해석할 수 있는 조건만 평가한다. 입장 마감·휴게시간·여러 운영 구간 등 필요한 조건을 해석하지 못하면 영향을 받는 평가를 UNVERIFIABLE로 기록하고 이유를 표시한다.
다만 방문일의 휴무처럼 독립적으로 확인된 위반은 유지한다. 같은 장소의 휴게시간을 해석하지 못해도 확인된 ADJUSTMENT_REQUIRED를 지우지 않는다.
독립적으로 확인된 위반과 해석하지 못한 조건은 같은 target에서도 조건별 근거를 구분하여 별도 평가 항목으로 남긴다. 일부 조건의 확인만으로 전체 운영시간 평가를 PASS로 만들지 않는다.
복잡한 운영시간 해석, 개장까지 자동 대기 또는 일정 재배치를 이 원칙의 필수 기능으로 요구하지 않는다. 구체적인 지원 형식·경계 비교는 해당 Rule 구현 전에 정한다.

### 일정 충돌

질문:

> 앞 일정과 다음 일정이 시간상 충돌하지 않는가?

일정 종료시간 초과도 확인한다. 유효한 입력의 최종 plannedStaySeconds 합계만으로 사용 가능 시간을 초과하면, 이동시간을 확인하지 못해도 IMPORTANT + ADJUSTMENT_REQUIRED로 평가한다.
이는 확인된 시간만으로 초과를 증명하는 판단이다. 이동시간 미확인 상태에서는 이를 0으로 확정하거나 정확한 총 필요시간·잔여시간을 생성하지 않는다.
체류시간 합계가 사용 가능 시간 이하라는 사실만으로는 이동·대기를 포함한 일정이 가능하다고 판단하지 않는다.

## 3. 지역 특화 Rule

질문:

> 해당 지역의 공공데이터 기준으로 통제 또는 위험 요소가 있는가?

현재 초기 지역:

- 부산

예를 들어 지역 공공데이터가 필요한 Rule은 반드시 `REGION` Scope를 가져야 하며 해당 지역 외 일정에 적용되면 안 된다.

## 4. Scope

### NATIONAL

지역에 관계없이 동일한 의미로 적용할 수 있는 규칙.

예:

- 이동시간
- 체류시간
- 일정 충돌

### REGION

특정 지역 데이터 또는 정책이 필요한 규칙.

예:

- 부산 지역 공공데이터 기반 통제 Rule

## 5. Importance

### NORMAL

일반적인 일정 품질 또는 편의에 영향을 주는 Rule.

### IMPORTANT

일정 실행 가능성에 큰 영향을 줄 수 있는 Rule.

### CRITICAL

발생 시 최종 판단에 반드시 반영해야 하는 Rule.

초기 Rule 분류·판정 집계·평가 상태는 [확정 공통 명세](09-diagnosis-contract.md)의 6절을 따른다. 신규 Rule과 날씨 위험 임계값은 해당 정책 작업에서 명시한다.

## 6. RuleResult가 표현해야 할 정보

최소 다음 의미를 표현할 수 있어야 한다.

- 어떤 Rule의 결과인가
- Rule Scope
- Importance
- 성공 / 경고 / 조정 필요 여부
- 검증 가능한 데이터가 충분했는가
- 판단 근거
- 문제 원인
- 사용자 조정 방법

구체 필드명은 구현 단계에서 정한다.

## 7. Rule 작성 원칙

- 하나의 Rule이 너무 많은 책임을 갖지 않는다.
- 외부 API를 직접 호출하지 않는다.
- 필요한 데이터가 없으면 거짓 판정을 생성하지 않는다.
- 지역 전용 Rule을 전국 공통 Rule 내부에 섞지 않는다.
- Rule 결과만으로 데이터 확인 실패를 숨기지 않는다.

## 8. 체류시간과 판정 불가

일정 계산은 활동이 이미 포함된 최종 plannedStaySeconds만 사용한다. 활동시간은 다시 더하지 않는다.
체류시간 Rule은 권장 총시간과 최종 계획시간을 비교하고, 추정 권장시간 부족은 CAUTION으로 표현한다.
최종 판정은 POSSIBLE / CAUTION / ADJUSTMENT_REQUIRED / UNDETERMINED이다. decision은 null이 아니다.
UNVERIFIABLE Rule을 정상 결과로 집계하지 않으며, 확인된 조정 필요는 UNDETERMINED보다 우선한다.

## 9. 근거의 적용 가능성과 지원 범위

- API 호출 성공과 해당 일정에 사용할 수 있는 근거인지를 구분한다. 해당 Rule에 필요한 적용 날짜·시간·대상 범위가 확인되지 않으면 영향을 받는 평가를 UNVERIFIABLE로 남긴다.
- 날짜 검증은 데이터별 계약에 따른다. 통제·운영정보의 적용 기간 확인을 모든 데이터에 일률적으로 요구하지 않으며, TMAP 조회 시점 예상시간의 사용 정책을 유지한다.
- CRITICAL 통제 판정도 해당 일정의 대상과 날짜·시간에 적용된다는 근거가 필요하다. 불명확한 통제를 확인된 방문 금지로 취급하지 않는다.
- 확인 불가 이유를 RuleResult와 coverage에 표시하고 가능한 다른 평가는 계속한다. 미지원 조건을 PASS 또는 NOT_APPLICABLE로 숨기지 않는다.
- 복잡한 예외를 모두 해결하거나 외부 데이터별 유효기간·갱신주기를 새로 정의하지 않는다. 지원하지 못하는 조건은 명시적으로 검증 불가 처리한다.

시간 계산·집계의 세부 계약은 [공통 명세](09-diagnosis-contract.md), 검증 사례는 [Evaluation Set](06-evaluation-set.md)의 EVAL-315~322를 따른다.
